# ADR-001: Выбор реляционной базы данных PostgreSQL

## Контекст и постановка задачи
Система FinHall должна обрабатывать финансовые транзакции. Нам нужна надежная база данных, которая гарантирует целостность данных (ACID) и поддерживает сложные запросы для формирования аналитики расходов.

## Драйверы решения
* Обеспечение строгой целостности финансовых данных.
* Поддержка сложных запросов (агрегация для графиков).
* Высокая надежность и отказоустойчивость.

## Рассмотренные варианты
* PostgreSQL
* MySQL
* MongoDB (NoSQL)

## Итог решения
Выбранный вариант: **PostgreSQL**, потому что она обеспечивает строгое соблюдение ACID, имеет отличную поддержку сложных аналитических запросов (оконные функции) и является стандартом де-факто для финтех-приложений с открытым исходным кодом.

### Последствия
* **Хорошо:** Надежное хранение транзакций, мощные инструменты аналитики.
* **Плохо:** Чуть более сложная настройка по сравнению с MySQL.

## Плюсы и минусы вариантов

### PostgreSQL
* Хорошо, потому что полная поддержка ACID и сложных запросов.
* Хорошо, потому что бесплатная и имеет огромное сообщество.

### MySQL
* Хорошо, потому что проще в базовой настройке.
* Плохо, потому что чуть менее гибкая в сложных аналитических запросах по сравнению с PostgreSQL.

### MongoDB
* Плохо, потому что не гарантирует строгую целостность транзакций по умолчанию (риск для банка).

# ADR-002: Использование JWT и Spring Security для аутентификации

## Контекст и постановка задачи
Приложению требуется безопасный механизм аутентификации клиентов и администраторов. Фронтенд (SPA) должен общаться с сервером без сохранения состояния сессии на сервере.

## Драйверы решения
* Безопасность (защита от CSRF, XSS).
* Масштабируемость (stateless архитектура).
* Простота интеграции с React-фронтендом.

## Рассмотренные варианты
* Сессии на основе Cookies (Stateful)
* JWT-токены (Stateless)
* OAuth 2.0 (через сторонний сервис)

## Итог решения
Выбранный вариант: **JWT-токены в связке со Spring Security**, потому что это обеспечивает stateless-аутентификацию, идеально подходящую для SPA на React. Токены будут храниться на клиенте и передаваться в заголовках `Authorization`.

### Последствия
* **Хорошо:** Сервер не хранит сессии, легко масштабируется.
* **Плохо:** Отзыв токена (logout) сложнее реализовать до истечения его срока действия.

## Плюсы и минусы вариантов

### JWT-токены
* Хорошо, потому что идеально для SPA (React).
* Плохо, потому что нельзя мгновенно отозвать токен без дополнительных механизмов (например, blacklist).

### Сессии (Cookies)
* Хорошо, потому что легко отозвать (удалить сессию).
* Плохо, потому что требует хранения состояния на сервере и сложнее настраивается для кросс-доменных запросов (CORS) с React.
