# ADR-001: Выбор реляционной базы данных PostgreSQL

## Контекст и постановка задачи
Система FinHall должна обрабатывать финансовые транзакции. Нам нужна надежная база данных, которая гарантирует целостность данных (ACID) и поддерживает сложные запросы для формирования аналитики расходов.

## Драйверы решения
* Обеспечение строгой целостности финансовых данных.
* Поддержка сложных запросов (агрегация для графиков).
* Высокая надежность и отказоустойчивость.

## Рассмотренные варианты
* PostgreSQL
* MySQL
* MongoDB (NoSQL)

## Итог решения
Выбранный вариант: **PostgreSQL**, потому что она обеспечивает строгое соблюдение ACID, имеет отличную поддержку сложных аналитических запросов (оконные функции) и является стандартом де-факто для финтех-приложений с открытым исходным кодом.

### Последствия
* **Хорошо:** Надежное хранение транзакций, мощные инструменты аналитики.
* **Плохо:** Чуть более сложная настройка по сравнению с MySQL.

## Плюсы и минусы вариантов

### PostgreSQL
* Хорошо, потому что полная поддержка ACID и сложных запросов.
* Хорошо, потому что бесплатная и имеет огромное сообщество.

### MySQL
* Хорошо, потому что проще в базовой настройке.
* Плохо, потому что чуть менее гибкая в сложных аналитических запросах по сравнению с PostgreSQL.

### MongoDB
* Плохо, потому что не гарантирует строгую целостность транзакций по умолчанию (риск для банка).

# ADR-002: Использование JWT и Spring Security для аутентификации

## Контекст и постановка задачи
Приложению требуется безопасный механизм аутентификации клиентов и администраторов. Фронтенд (SPA) должен общаться с сервером без сохранения состояния сессии на сервере.

## Драйверы решения
* Безопасность (защита от CSRF, XSS).
* Масштабируемость (stateless архитектура).
* Простота интеграции с React-фронтендом.

## Рассмотренные варианты
* Сессии на основе Cookies (Stateful)
* JWT-токены (Stateless)
* OAuth 2.0 (через сторонний сервис)

## Итог решения
Выбранный вариант: **JWT-токены в связке со Spring Security**, потому что это обеспечивает stateless-аутентификацию, идеально подходящую для SPA на React. Токены будут храниться на клиенте и передаваться в заголовках `Authorization`.

### Последствия
* **Хорошо:** Сервер не хранит сессии, легко масштабируется.
* **Плохо:** Отзыв токена (logout) сложнее реализовать до истечения его срока действия.

## Плюсы и минусы вариантов

### JWT-токены
* Хорошо, потому что идеально для SPA (React).
* Плохо, потому что нельзя мгновенно отозвать токен без дополнительных механизмов (например, blacklist).

### Сессии (Cookies)
* Хорошо, потому что легко отозвать (удалить сессию).
* Плохо, потому что требует хранения состояния на сервере и сложнее настраивается для кросс-доменных запросов (CORS) с React.

# ADR-003: Использование библиотеки iText для генерации PDF

## Контекст и постановка задачи
Во время второго раунда переговоров Заказчик запросил новую функцию экспорта выписки по счету в PDF. Нам нужна библиотека, которая сможет быстро и надежно генерировать PDF-документы с таблицами транзакций.

## Драйверы решения
* Быстрая интеграция со Spring Boot.
* Поддержка кириллицы и табличного вывода.
* Возможность поручить разработку Junior-разработчику.

## Рассмотренные варианты
* iText (или OpenPDF)
* Apache PDFBox

## Итог решения
Выбранный вариант: **iText**, потому что она предоставляет удобный высокоуровневый API для создания документов и таблиц, что позволит Junior-разработчику быстро справиться с задачей.

### Последствия
* **Хорошо:** Быстрая генерация отчетов, легко читаемый код.
* **Плохо:** Добавление новой зависимости в проект (увеличение размера сборки).

## Плюсы и минусы вариантов

### iText
* Хорошо, потому что простой API для таблиц и текста.
* Хорошо, потому что большое количество примеров в документации.

### Apache PDFBox
* Хорошо, потому что полностью бесплатный (Apache License).
* Плохо, потому что требует написания большего количества низкоуровневого кода для позиционирования элементов.

# ADR-004: Моделирование динамического поведения системы с помощью UML

## Контекст и постановка задачи
В рамках лабораторной работы №5 возникла необходимость спроектировать модель динамического поведения системы FinHall. Требовалось отразить взаимодействие пользователей с системой во времени, включая логику бизнес-процессов (перевод средств), жизненный цикл сущностей (учетная запись) и обмен сообщениями между компонентами (аутентификация). Для этого нужно было выбрать нотацию и инструмент моделирования.

## Драйверы решения
* Необходимость визуализации требований для команды разработчиков и Заказчика.
* Возможность описать как общую логику (Use Case), так и детали (Activity, State, Sequence).
* Требование использования стандартной нотации (UML 2.5.1).
* Инструмент должен поддерживать экспорт в PDF для включения в отчетную документацию.

## Рассмотренные варианты
* **Текстовое описание UML (PlantUML)**
* **Визуальное моделирование в Microsoft Visio**
* **Онлайн-инструменты (Draw.io, Visual Paradigm)**

## Итог решения
Выбранный вариант: **Microsoft Visio** как основной инструмент визуализации, с ручным контролем соответствия нотации UML 2.5.1. 

Для описания связей на диаграммах используются следующие механизмы:
1. **Диаграмма вариантов использования (Use Case):** 
   * Связь `<<include>>` используется для отражения обязательных зависимостей (например, любой прецедент требует аутентификации). 
   * Ассоциации показывают, какие актеры инициируют прецеденты. 
   * Внешние системы (Почтовый сервис, API курсов валют) вынесены за границы системы.
2. **Диаграмма активности (Activity):** 
   * Ромбы (Decision nodes) используются для ветвления логики (проверка лимитов, баланса). 
   * Guard conditions (условия на стрелках) показывают, при каких условиях происходит переход.
3. **Диаграмма состояний (State Machine):** 
   * Состояния описывают жизненный цикл сущности (аккаунт: Зарегистрирован → Активен → Заблокирован → Удален). 
   * Переходы инициируются событиями (вход, блокировка администратором, запрос на удаление).
4. **Диаграмма последовательности (Sequence):** 
   * Lifelines (линии жизни) отражают участников процесса (Web, AuthController, AuthService, БД, Почтовый сервис). 
   * Синхронные и асинхронные сообщения показывают порядок вызовов и возврат данных.

### Последствия
* **Хорошо:** Единая нотация для всех диаграмм, понятная команде и Заказчику. Все диаграммы экспортированы в PDF и встроены в SDD.
* **Плохо:** Ручное рисование в Visio занимает больше времени, чем генерация из текста (PlantUML), но дает полный визуальный контроль.

## Плюсы и минусы вариантов

### Microsoft Visio
* Хорошо, потому что полный контроль над внешним видом и расположением элементов.
* Хорошо, потому что поддерживает экспорт в PDF и интеграцию с офисными документами.
* Плохо, потому что требует ручной работы (нет автоматической генерации из текста).

### PlantUML
* Хорошо, потому что быстро (текстовое описание генерирует картинку).
* Плохо, потому что ограниченный контроль над расположением элементов (автоматическая раскладка).

### Draw.io / Visual Paradigm
* Хорошо, потому что бесплатные и онлайн.
* Плохо, потому что могут иметь ограничения на экспорт в PDF в бесплатных версиях.
